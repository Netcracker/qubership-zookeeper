Principles
One skill is one decision to load. Everything in it must apply whenever its description matches, so the triage discipline of a whole tracker is one skill, while "everything about Kafka" is not — a consumer-lag ticket would carry the broker-installation part in with it.
The description decides invocation. The analyst session sees the name and description of every installed skill and invokes the ones that fit, so write symptoms, tracker names, and error signatures rather than a summary.
Visibility metadata decides installation. The visible-for-* keys control which tickets see the skill at all; without them it is offered everywhere.
The body is instructions for a run. Concrete commands, log locations, decision steps — leave out background theory.
Test the skill on a real ticket before you merge it. A skill nothing triggers is dead weight.
Bundle Layout
A bundle is a directory in Git, and the Git path of the bundle must point at it. Each skill lives in its own directory under .apm/skills/:

my-bundle/                  ← the bundle's Git path points here
├─ apm.yml                  ← manifest
└─ .apm/
   └─ skills/
      ├─ troubleshoot-kafka/
      │  ├─ SKILL.md
      │  └─ broker-error-codes.md   ← optional reference material
      └─ ocs-ssh-connect/
         └─ SKILL.md
Skill Format
Each skill is a SKILL.md file in the Agent Skills format: YAML frontmatter, then the instruction body. Use the directory name as the name in the frontmatter, so that the name and the folder on the nodes are the same. The check does not require this.

---
name: troubleshoot-kafka       # use the directory name
description: >-
  Use when consumer lag grows, brokers flap,
  or ISR shrinks after a broker restart.
---

1. Check controller logs at /var/log/kafka/ …
Supporting Files
A skill can carry more than its SKILL.md. Every file in the skill's directory ships with it, so the body can name one and the analyst opens it when a step calls for it.

Keep the procedure in SKILL.md and move out reference material only. What separates the two is what the analyst does with the content: an error-code table, the layout of a diagnostic pack, or a long list of component names is looked up when a step points at it, whereas a step is followed. A step that lives outside SKILL.md is a step the analyst can skip, because the assessment runs unattended and nobody is there to notice the file it never opened.

Length alone is rarely a reason to split. The five skills that ship with the product hold their whole procedure in one file, between 120 and 360 lines each. When a document does outgrow that, prefer two skills whose descriptions choose between them over one skill that spreads its procedure across files.

Validation
Only the directory .apm/skills/<name>/ is copied to the nodes. A file elsewhere in the repository does not exist for the analyst, so a skill must be self-contained: keep every file it uses inside its own directory and link to it with a relative path.

A symlink inside a skill directory is allowed. The sync copies the file that the symlink points to, so the analyst gets a regular file with that content, not a link. This lets several skills share one file of the same repository. The sync follows a symlink only when its target is a regular file in the repository of the bundle, and outside the .git directory. It skips every other symlink and does not fail the bundle. The skipped symlinks are:

a symlink to a file outside the repository, for example an absolute path such as /etc/hosts
a symlink to a file in the .git directory
a symlink to a directory
a symlink to a file that does not exist
A file of a dependency is not part of the repository of the bundle. To use it, copy it into the repository of the bundle. A Markdown link to a skipped symlink is reported as a missing file.

Each sync, and each check in the Add and Edit dialogs and in the trial run, reads every skill and lists the problems it finds as issues. The check covers the skills of the bundle and the skills of its dependencies. The issues are listed under the name of the skill they belong to, and they never block a bundle. Every other skill in the bundle is still installed.

An issue is either critical or not:

Critical. The issue prevents the model from loading or discovering the skill. The skill is not published, so no assessment gets it.
Not critical. The issue does not prevent the model from loading the skill, but it might affect the quality of the assessment.
The checks are:

SKILL.md has valid YAML frontmatter. Without it, the model cannot discover the skill (critical).
name is present, is a string and is not empty. Otherwise the model cannot discover the skill (critical).
name holds none of the characters that Claude Code refuses: control and zero-width characters, characters that change the text direction, private-use or unassigned characters, < and >, and any space other than one plain space between words. Otherwise the model cannot discover the skill (critical).
description is present, is a string and is not empty. Otherwise the model cannot discover the skill (critical).
name has at most 128 characters and description has at most 1536 characters. A longer text takes too much space in the model context (critical).
Every Markdown link in the skill body and in the other Markdown files of the skill points to a file that exists in the skill directory. The model might not find the file, which might affect the quality of the assessment (not critical).
The Agent Skills specification at agentskills.io sets lower limits: 64 characters for name and 1024 characters for description. Not every AI harness enforces them strictly, so Bill does not enforce them either. Bill still needs a hard limit, so it uses 128 and 1536 characters. This is an accepted deviation from the specification. A skill that follows the specification always passes the check.

The link check ignores fenced code blocks, inline code and web links. A link that leaves the skill directory is reported as a missing file, because only the skill directory is copied to the nodes. The issue text is "the referenced file is absent in the skill directory or has not been installed".

For example, ../../instructions/tickets.md fails the check even when the file exists in your repository. Move tickets.md into the skill directory and link to it as tickets.md.

Each issue links to the file and line that hold the problem. The link opens the repository that supplied the skill, at the commit that was checked. For a skill that comes from a dependency, this is the repository of the dependency, not the repository of the bundle. A skill from a local path has no link. The same links appear in the popup that opens when you point at a skill name that has issues, in the Skills column of the bundle list.

The optional fields and the body are not checked for length.

Metadata Reference
Key	Required	Description
name	yes	Skill id. Use the skill's directory name, in kebab-case.
description	yes	When the skill applies. The analyst invokes skills by description.
netcracker.com/visible-for-ticket-boxes	no	Offer the skill only for tickets in these ticket boxes.
netcracker.com/visible-for-domains	no	Offer the skill only for tickets in these domains.
netcracker.com/visible-for-pipeline-assessment	no	Offer the skill only for pipeline assessments.
The visibility keys go under metadata:, take a comma-separated list, and are matched case-insensitively.

visible-for-ticket-boxes
By default a skill is offered for every ticket. This key limits it to the listed ticket boxes — the part of the Jira key before the hyphen, so PSUPICEOC-1904 belongs to the PSUPICEOC box.

---
name: nrm-tickets-triage
description: >-
  Tracker hierarchy and triage rules
  for Cloud NRM tickets.
metadata:
  netcracker.com/visible-for-ticket-boxes: PSUPICEOC, PSUPICE, RMCR
---
A misspelled name raises no error: the skill is simply never offered. Copy the exact ids from the Ticket Boxes page.

visible-for-domains
The same idea one level up, for skills that apply to a whole product area whatever the tracker — deployment guides, product architecture, and the like.

---
name: backup-restore-troubleshooting
description: >-
  Use for backup or restore failures
  in any platform component.
metadata:
  netcracker.com/visible-for-domains: OCS, NRM, Platform
---
How the two keys combine:

Neither key is set, so the skill is universal and offered for every ticket.
Both keys are set, and they are combined with OR: the skill is offered when the ticket's box is listed or its domain matches.
Visibility gates installation only. The description still decides whether the analyst invokes the skill.
A disabled bundle is never offered, whatever the keys say, and on a name collision the built-in skill wins.
Domain names are in the domain switcher at the top of the menu, and on the Domain badge of any bundle.

visible-for-pipeline-assessment
This key is optional. A skill with "true" here is offered for pipeline assessments of the Build Cop, and only there, so it never affects ticket assessments:

---
name: my-component-pipeline-assessment
description: >-
  Use when a pipeline of my-component fails.
metadata:
  netcracker.com/visible-for-pipeline-assessment: "true"
---
Use the key to keep a pipeline skill out of ticket assessments. A skill without it is universal and is offered for pipeline assessments as well as for tickets, so a pipeline skill without the key can influence ticket assessments too. The ticket-box and domain keys do not apply to pipelines.

Pipeline Assessment Skills
A pipeline skill teaches the agent how one component's pipeline is built and what its failures mean. To adopt the Build Cop for a component, follow the Onboarding Guide; this section covers only the skill.

Add netcracker.com/visible-for-pipeline-assessment: "true" to limit the skill to pipeline assessments, as described under visible-for-pipeline-assessment. Then use the body to tell the agent:

how to read the stages, jobs and job artifacts, and which job names matter;
how to classify a failure, for example product bug, test bug, or infrastructure;
which actions to recommend for the different issues, for example restart job, revert MR, file a bug or escalate to the responsible team;
which issues to put first when several jobs fail;
which artifacts and logs to open for each kind of failure.
For a complete example, see the Infra.Automation pipeline assessment skill. Before you publish, try the skill on a real failed pipeline, as described in Trial run.

Trial run
A skill can be tried on one ticket before it is published. On the tickets page, open Request assessment and enable Try an unpublished skill bundle on this run — the same Git URL, ref, and path fields as Add Bundle appear. The source must be a valid APM bundle root (apm.yml). The run is always record-only: the Jira ticket is never commented on or moved.

A pipeline can be tried the same way. On the Pipelines page, open Request assessment, select the Git project, and enable Try an unpublished skill bundle on this run. The access check runs as the domain of that Git project, so it starts only after you select the project. A trial run on a pipeline never sends a Webex notification. It also does not replace a normal run: a CI trigger for the same pipeline still gets its own assessment, and the trial run is compared with the last normal run of that pipeline.

Install order on that run is bundled skills, then published APM skills, then the trial bundle. A trial skill with the same name as a stored skill replaces it for this run only; a new name is added. Visibility keys (visible-for-*) are ignored for the trial overlay.

The clone lives only in that assessment's workdir. The node's published skills volume is not written, and the SkillBundle catalogue is not updated. After the run the workdir is deleted.

The Skills tab lists every trial skill whether the analyst invoked it or not, with source attached. Production statistics, Grafana aggregates, and the feedback export omit trial rows. The assessment counts of a Git project and the Pipelines menu count also omit trial runs.

Available Tools
The tools below are what the analyst session can call. The set is fixed by the platform: a skill cannot add a tool, and it does not need to declare the ones it uses. What a skill contributes is the judgement around them — which tool answers which question, what to look at in the output, and when the answer is good enough to stop.

Name a tool the way the agent sees it, exactly as spelled here. Several tools are offered only when the ticket's domain has the matching feature configured, which each section notes.

This list is generated from the worker, so it is what the current release actually offers.

Sandbox Environment
The Bash tool runs inside a fixed container. The skill can create files freely under the working directory, but the rest of the filesystem is read-only, and the only way out to the network is the tools listed above plus curl against URLs that the ticket itself references.

Nothing can be installed. Write instructions against the commands below and nothing else, because a skill that reaches for a missing utility fails at the point where the analyst needed the answer.

Available Commands
Shell and coreutils: bash, sh, env, cat, cut, head, tail, tr, sort, uniq, wc, find, grep, sed, awk, tee, xargs, ls, mkdir, rm, cp, mv, chmod.
Archives and compression: tar, unzip, gzip, gunzip, bzip2, bunzip2, xz, unxz.
Data tools: jq, python3, diff, cmp, patch, file, xxd, strings.
Network: curl, and only for URLs the ticket links to. GitLab, Jenkins, and Jira are reachable through their tools alone — a raw curl to those hosts carries no credentials and fails.
Present but constrained: git, ssh, openssl. Source code arrives through the repo tool, which mounts a branch on disk, so a skill never needs git clone.
Not available: wget, rsync, node, npm, and package managers such as apt and pip. Never write a step that installs something.

Two habits are worth stating in a skill that drives Bash. Read files larger than 1 MB through grep or a script rather than the Read tool, which spends the analyst's context on them. Leave everything under attachments/ untouched, because the raw attachments are the evidence; unpack into a sibling directory and work on that copy.

Python
python3 is the standard library plus one third-party module, PyYAML, imported as yaml. The modules that earn their place in a skill are json, re, csv, sqlite3, hashlib, gzip, tarfile, zipfile, tomllib, datetime, html.parser, xml.etree, and urllib.

Installing a new module is not possible: there is no pip, and the filesystem outside the working directory is read-only. If a procedure needs a library that is not there, rewrite it around the standard library.

Prefer Python over Shell Scripts
Anything longer than a single command belongs in Python — either python3 -c '...' for a couple of lines, or a .py file written into the working directory and run. Reserve the shell for one self-contained command, such as a grep over a log, an unzip, or a head.

Failures stay visible. A Python error is a traceback that names the line; a shell pipeline reports the exit code of its last stage, so a failure in the middle passes for success.
Structured data is parsed, not matched. JSON, CSV, and YAML go through a parser that understands quoting and nesting, instead of grep and awk patterns that break on the first unusual record.
Multi-step logic stays readable. Conditions, loops, and intermediate results are easier to follow, and easier for the analyst to correct when a step returns nothing.
